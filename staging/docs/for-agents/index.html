Shunter guide for AI agents

Use this page as the entry point when authoring or migrating Flowbooks. The schema is authoritative; do not guess keys. Use <path-to-shunt> schema to print the schema from your downloaded runner, or read the published Flowbook schema linked from the documentation site. Invoke the runner using the path where you installed or downloaded it; it need not be on PATH.

Authoring checklist

Section titled “Authoring checklist”
  • Read Flowbook format, the task reference, known limitations, and the CLI reference. Pick the closest migration gallery example and copy its structure and style. Keep its wrapper beside the original CI configuration.
  • A Flowbook is a YAML mapping with flows; each Flow has id, name, and ordered tasks. A task has id, type, and task-specific properties. Child tasks use children where the task schema permits it. The schema lists all legal keys and required values.

set-variable

Section titled “set-variable”

With source: TaskOutput, set-variable reads the selected prior task’s logged output (combined stdout and stderr when logging is enabled), not its output-variable. An empty source-task means the previous executed task in the same flow, call and iteration. A non-empty regex selects regex-group (default 1); if it does not match, the task fails. Use a producer’s output-variable followed by extract-text when you need captured process output regardless of logging, or need extract-text options such as match-index, multiline or case-insensitive matching.

Section titled “if”

The condition is a Python expression. It is evaluated for truth, and Flow variables are available in the variables dictionary by name. For example, variables.get("RunTests") == "true" reads the RunTests Flow variable. The expression also receives env (the process environment mapping), task and workflow namespaces, the flow API object, and Python built-ins. Use quoted strings for Flow variable values.

Flowbook style for CI migrations

Section titled “Flowbook style for CI migrations”

Shunter assigns a generated task name when name is omitted. The name is based on the task type and the task’s identifying properties, such as a command or path, so keep it where possible. Use exactly one nonblank comment task immediately above each task it labels; its name must exactly match properties.comment. Comment text says what the step does, not where it was migrated from, and does not repeat the command shown by the task. Put provenance, rationale, flags and other extra context in that comment task’s task-level description. Put a Flow overview in the Flow’s description, not in another comment above the first task’s label. Use a blank comment task only as a visual spacer between logical steps or groups when it improves readability. Comments are presentational: put executable behavior in task properties and preserve the upstream command semantics.

CI concept mapping

Section titled “CI concept mapping”
CI concept Flowbook or wrapper Limits and migration action
Jobs Tasks in a main Flow by default Put the developer checks (tests, typing, lint, docs) in one ordered Flow. Split only for distinct triggers or side effects, such as tag releases, package publication or deploys. Each CI wrapper job can run the full Flow or a task-selected part of it.
Steps Tasks Use run-command for existing scripts and commands.
Matrix Wrapper matrix; pass a Flow variable only when the Flow reads it Matrix cells remain separate CI jobs/runners. Wrapper setup such as setup-node selects tool versions without a Flow variable; pass values used by Flow commands, such as a tox environment, build configuration or CMake preset.
Environment Flow/task environment; --var for Flowbook values Provider environment and secret injection stay in CI.
Secrets CI secret store, injected environment Never copy secret values into a Flowbook or report.
Caches CI cache action/plugin No portable cache equivalent; keep cache management in the wrapper.
Artifacts Task artifacts; publish-artifact; provider upload Provider retention and cross-job transfer remain provider-specific.
Conditions if, else-if, else, fail-if, enabled/conditions where supported Provider event/permission conditions remain in CI.
Services/containers Existing container command via run-command, if locally available No general service orchestration equivalent; keep setup and lifecycle in CI or project scripts.
Triggers CI wrapper Flowbooks do not schedule runs.
Reusable workflows run-flow for shared Flowbook logic Provider reusable workflow inputs/permissions remain in CI.

Map ordinary developer checks into one ordered main Flow by default, such as tests, typing, lint and documentation checks. Matrix entries allocate separate provider jobs that call the same Flow. Wrapper setup steps such as setup-node and setup-python select the toolchain and need no Flow variable. Pass a matrix value only when a Flow command reads it, such as a tox environment, build configuration or CMake preset. Keep separate Flows for work with a different trigger or side effect, such as tag releases, package publication or deploys. A wrapper job can call the whole Flow or select part of it with one CLI selector option (--task, --from, --to, or --selection) per invocation. Selecting a comment task fails with the normal clear unmatched-selector diagnostic; select the next executable task instead.

When a test script ends with the test runner, append its JUnit flags to the invocation (for npm scripts, after npm test --). For a chained script such as tsc && xo && node --test, npm sends appended flags only to the last command. Prefer separate lint, typecheck, and test tasks, with the JUnit artifact declared only on the test task; this identifies the failing step and avoids a missing required JUnit file error for earlier failures. Appending flags to a chain is acceptable when the test runner is last and that behavior is intended. A missing required JUnit file does not add a second artifact error after the task command has failed.

Validate and run until green

Section titled “Validate and run until green”
  1. Run shunt validate path/to/build.flowbook. For a selected flow, add --flow <id-or-name>. Use --format json to consume stable issue fields (severity, file, line, column, path, code, message, hint). Human output is the default; apply its fix hints and validate again.
  2. Run the same Flow locally: shunt run path/to/build.flowbook --ci none (or shunt path/to/build.flowbook --ci none). Use the same tool versions and inputs as CI.
  3. Read the generated HTML report and its JSON sidecar. In JSON, inspect the top-level runStatus and errorMessage, then each task’s status, failureMessage, and attempts entries (exitCode and message). Find the first failed task in execution order; it usually explains downstream skips. Fix the cause and repeat validation and run until green.
  4. Compare tests, artifacts, exit behavior, and failure paths with the original CI. Report every mapping, gap, and assumption.

A run-flow task with properties.flowbook naming another Flowbook resolves relative to the calling Flowbook. The called Flow is selected by properties.flow. Do not put ${RepoRoot} in that path: it is not expanded.

Common mistakes

Section titled “Common mistakes”
Wrong Right
Put stop-on-failure or output-variable inside properties. Put them beside properties at task level.
properties: {flowbook: '${RepoRoot}/ci/build.flowbook'} properties: {flowbook: 'ci/build.flowbook'} (relative to caller).
Export empty CC/CXX variables on every platform/job. Set toolchain variables only for jobs that need them; otherwise inherit the runner environment.
Capture a source commit with a regex that has no capture group. Use a capturing group and validate the captured value on a real log line.
Read TaskOutput as an output variable. It reads the selected prior task’s combined logged output (stdout and stderr when logging is enabled). To extract captured process output, set output-variable on the producing task and pass ${Variable} to extract-text. A regex no-match fails set-variable.
Publish JUnit even when no test command ran or the file is empty. When the upstream test runner can emit JUnit (for example pytest --junitxml, jest-junit, or ctest --output-junit), add that flag to the test task only and attach its produced file. This is the one allowed change to an upstream command; note it in the task’s description. Never attach a file the command does not produce.

Follow the first CI report walkthrough. Use the documented CI migration guidance and provider wrapper examples. Check the original CI’s actual commands before adopting examples. For release pipelines, preserve signing, packaging, versioning, and publication steps explicitly, then verify each output before changing required checks.
