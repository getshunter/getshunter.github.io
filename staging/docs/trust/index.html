What Shunter does

Shunter runs a YAML Flowbook locally or through your existing CI provider. The desktop app edits and debugs it; shunt executes it. This page describes the current preview, not planned services.

Telemetry and network access

Section titled “Telemetry and network access”

The desktop app and runner do not make background telemetry or phone-home requests. The runner includes a user-invoked Download File task, and Flowbook commands and Python scripts can also use the network. Network use is tied to a task or script the user selects, not an automatic product service.

The GitHub Action downloads the exact-version runner archive and checksum from the configured GitHub release, verifies it and caches the extracted runner. Its workflow invokes actions/cache@v4, actions/upload-artifact@v7, and dorny/test-reporter pinned to commit a43b3a5f7366b97d083190328d2c652e1a8b6aa2. The Action uploads HTML reports, requested task artifacts and summaries/test results to GitHub. GitHub also hosts the workflow logs and cache. The runner archive contains a bundled Python runtime. Its worker performs network access only for a Flowbook Download File task or network-using script; it has no background service.

The desktop app and runner do not contact Shunter servers automatically, check for updates, send usage data, or upload files. They have no remote-debugging connection in this preview. Network activity caused by a Flowbook task remains the user’s choice.

In practical terms, the desktop app does not register itself, fetch a licence, poll for releases, or send a crash report. The runner does not register builds, phone home with run outcomes, or send reports to Shunter. There is no hosted Shunter service in this preview.

When a Flowbook uses Download File, the runner performs the requested HTTP(S) download. A Run Command, Run PowerShell Script or Run Python Script task can also make network requests through the programs it starts. Those tasks run with the current user’s or CI agent’s normal permissions and network access.

The GitHub Action is different because it installs and integrates the runner in GitHub Actions. It downloads the selected runner version and its checksum from the configured GitHub release repository. The installer validates the checksum and executable version before caching the runner under the runner’s temporary directory.

The Action uses GitHub’s cache for that runner installation. After the run, it can upload the HTML report and Flowbook artifacts to GitHub Actions artifact storage, where the Action sets a 14-day retention period. When JUnit paths are produced, it invokes the pinned test-reporter action unless the run is cancelled; fork pull requests skip that step. It publishes the Markdown summary through the GitHub Actions summary mechanism. These transfers are visible in the workflow run.

GitHub Actions itself also stores the workflow definition and execution logs. Shunter does not control the provider’s retention, access policy or account security settings. Configure those in GitHub.

Where data goes

Section titled “Where data goes”

Local runs write output and reports to the paths you choose. HTML, JSON and Markdown reports are files on your machine unless you share or upload them. The GitHub Action uploads its configured HTML report and Flowbook-declared artifacts to GitHub Actions storage. Review reports before sharing: they can contain task output, variable and environment context, paths, and report links that reveal file locations or artifact URLs.

The GitHub Action’s default HTML report path is .shunter/report.html; its JSON and Markdown reports use the same file stem. A local runner’s automatic HTML filename is derived from the Flowbook path and run ID. You can choose another report destination with runner options. Shunter does not sync local reports to an account or send them to the website.

Run records can include task names and descriptions, task output, execution commands and working directories, run inputs, environment metadata, timings, resource summaries and artifact references. The report’s relative links may open files or CI artifacts when available. A report is therefore useful to attach to an issue, but inspect its content and links first, especially if the repository or build paths are private.

The HTML report is a self-contained, shareable run record. Its local file path is not uploaded by a local run. In CI, the Action’s artifact step is what transfers the selected report to GitHub. Other providers use their own configured artifact collection and retention policies.

Mark secret Flowbook variables with sensitive: true and avoid printing secrets from commands. Shunter redacts known sensitive values across run output and reports, but it cannot identify every secret or every transformed representation. A report is not a secure secret store.

Treat Flowbooks from pull requests as code. They can run commands and scripts with the permissions of the local user or CI agent. In particular:

  • Review Flowbook changes from forks before executing them.
  • Do not pass secrets to untrusted pull-request jobs.
  • Keep CI permissions limited to what the job needs.
  • Inspect report content and artifact paths before sharing them outside the project.

Shunter does not provide a command sandbox. File access, subprocesses and network access follow the operating system and CI agent permissions available to the run.

Integrity and release plans

Section titled “Integrity and release plans”

Runner archives currently include SHA-256 sidecars. A checksum can detect accidental corruption or a mismatch against a trusted sidecar; it does not authenticate an unsigned publisher. The first preview is unsigned. Signed releases are planned, with no date committed. An SBOM is planned, with no date committed.

The checksum sidecar is a text file containing the archive’s SHA-256 digest and filename. Download the archive and sidecar from the same release, then follow the Windows or Linux commands in the README. Do not compare against an independently untrusted checksum and treat that as a signature.

The desktop installer and AppImage do not currently receive their own checksum sidecars from the packaging jobs. The documented verification steps cover runner archives.

“Generated by Shunter”

Section titled ““Generated by Shunter””

The line appears in generated CI wrapper comments to identify the generator. It contains no tracking identifier or network beacon. This preview has no setting that removes the line.

The marker is plain text in the generated file. It is not a unique user or installation ID, and it does not cause a request. Generated wrappers still contain provider-specific install and run steps, so review the resulting file before committing it.

Check for yourself

Section titled “Check for yourself”

You can observe a desktop run with Windows Firewall or Process Monitor, and a Linux run with strace -f -e trace=network. Check the process tree while executing a Flowbook task that does not itself use the network. For an Action run, inspect the workflow steps and GitHub’s cache, artifact and summary records; those GitHub transfers are part of the Action’s documented CI behavior.

For a clean observation, use a small Flowbook containing only a local command and no Download File task. Watch both the desktop process and its child processes while it runs. Then add one Download File task and compare the new traffic with the task’s configured URL.

For the Action, inspect the exact workflow revision and all uses: references. The cache key includes operating system, architecture and runner version. The artifact and summary steps show which files and content leave the job. Keep job permissions as narrow as your workflow allows and avoid exposing secrets to untrusted pull-request code.

These checks can confirm the behavior of the version you downloaded. They do not prove that a different build, modified binary, operating system, CI provider or Flowbook is safe.
