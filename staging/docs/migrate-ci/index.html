Migrate an existing CI build to Shunter

Give your coding agent the existing workflow, the repository, and a recent CI run to compare against. The agent moves build commands into a Flowbook you can run locally and in CI. The provider still schedules jobs, sets up the runner, manages credentials, and publishes anything that depends on its APIs.

Install shunt and try a local run first if you are new to Shunter. Quick start.

Instructions for a coding agent

Section titled “Instructions for a coding agent”

For an agent-neutral, copy-paste task prompt, use the migration prompt. First give the agent the self-contained guide for AI agents, which links the format, task, schema, validation and reporting contracts.

Copy this prompt into your agent and fill in the workflow path and baseline run.

Migrate the build and test pipeline in <workflow path> to Shunter. Use <commit or CI run URL> as the baseline. Read the workflow, any scripts or reusable jobs it calls, and the project’s build documentation. Identify what happens on success, failure, and each supported platform. Then add a Flowbook and a CI wrapper that can run beside the existing pipeline. Use the checked-in project scripts where they already express the build. Show how to validate and run the Flowbook locally. In your report, map every original job or step to its new location or explain why it is still in the original pipeline. Record the tests, artifacts, and failure paths you verified. Mark behavior you could not verify and name any decisions needed before switching the required CI checks.

Pick the closest migration gallery example and copy its structure and style. Follow the first CI report walkthrough; keep the generated wrapper alongside the original CI.

Use this order to carry out the migration.

  1. Record the baseline. Record the commit, runner image or agent label, tool versions, matrix entries, and trigger. For each job, capture its commands, working directories, shell, environment, conditions, and outputs. Follow reusable workflows, Jenkins shared libraries, and third-party actions far enough to establish what the build consumes and produces. Record secret names and scopes without recording values.
  2. Decide where each step belongs. Move portable configure, build, test, and package commands into named Flowbook tasks. Keep triggers, matrices that allocate separate runners, checkout, tool installation, caches, service containers, permissions, and credentials in the provider wrapper where applicable. Keep provider-specific publishing and fingerprints there too. Preserve failure behavior, including which steps run after a failure. If a step has no clear equivalent, keep the original step or flag it in the report.
  3. Run locally. Use the same tool versions and inputs as one CI job, and run on the same OS family when possible (for example, Linux under WSL for an Ubuntu job). Windows run-command uses ComSpec, where built-ins such as del, copy, and rd can take precedence over package binaries in node_modules\.bin; upstream npm scripts may therefore behave differently. Waited command tasks have empty stdin, so interactive prompts fail fast. Pass non-interactive flags such as /q, -y, or --yes, or set CI=true. If your local OS differs from CI, record that in the report instead of editing upstream scripts. Run shunt validate, then shunt run, and inspect the resulting HTML report. Check that the expected tests actually ran. Open the same Flowbook in the desktop app if you want to step through it.
  4. Compare old and new runs. Run both against the same commit in separate workspaces. Compare matrix coverage, test names and outcomes, package contents, exit status, and logs and artifacts available after a failure. In a disposable branch or checkout, make one test fail and confirm the migrated job fails and still publishes its run report. Update required checks or downstream jobs only after the new job passes the comparison.

For each row in the migration report, record the original step, its new location, the result you expected, and the evidence you observed. Mark anything you only checked locally or could not run on the provider. The two examples below show what that mapping looks like.

Flowbook authoring style

Section titled “Flowbook authoring style”

Keep Shunter’s generated task name wherever possible. Shunter builds that name from the task type and identifying properties such as a command, path, or operation. Use exactly one nonblank comment task immediately above the task it labels; set its name to the same text as properties.comment. Comment text says what the step does and does not repeat its command or mention migration provenance. Put extra context such as origin, rationale, or added flags in that comment task’s task-level description; put a Flow overview in the Flow’s description. Blank comment tasks may serve as visual spacers. Comments remain in the Flowbook and editor but do not appear in run output or task totals; task selectors should name executable tasks. Keep comments presentational and preserve upstream command semantics. The agent guide has a validated example.

Map jobs into Flows

Section titled “Map jobs into Flows”

The default is one main Flow containing the ordered checks a developer would want to run locally, such as tests, typing, lint and documentation checks. Matrix cells stay as separate provider jobs/runners and call that same Flow. Wrapper setup steps such as setup-node or setup-python select the toolchain and need no Flow variable. Pass a matrix value only when the Flow itself reads it, such as a tox environment, build configuration or CMake preset. Split work into separate Flows only when its trigger or side effects differ, such as tag-only releases, package publication or deploys. A wrapper job may run the whole main Flow or a portion by selecting task IDs with --task; preserve provider triggers, runner allocation, caches and cross-job dependencies in the wrapper.

Each matrix wrapper invocation passes its build variant to the same Flow with shunt main.flowbook --flow main --var BuildVariant=<matrix-value>, because the Flow commands read it. Wrapper setup steps such as setup-node or setup-python select the toolchain and need no Flow variable. Pass a matrix value only when the Flow itself reads it, such as a tox environment, build configuration or CMake preset. A wrapper can instead select part of the Flow with --task, --from, --to, or --selection (use one selector option per invocation).

Publish test results in the Shunter report

Section titled “Publish test results in the Shunter report”

Attach a test-result declaration to the task that runs the tests. Each artifacts item accepts exactly these keys: path (required glob), type (required: file, junit, trx, or nunit), name (optional display name), required (optional boolean, defaults to true), and fail-on-failed-tests (optional boolean for junit, trx, or nunit, defaults to true; invalid on file). Unknown keys are rejected. When the upstream test runner can emit JUnit (for example pytest --junitxml, jest-junit, or ctest --output-junit), add that flag on the test task only and attach the resulting file there. This is the one allowed change to an upstream command; note it in the task’s description. Never attach a file the test command does not produce.

Use the project’s actual build directory, configuration, test filters, and shell syntax. Shunter parses each matching result file, adds its cases to the run report, and publishes a sanitized JUnit result. Failed or errored test cases fail the task by default; set fail-on-failed-tests: false only when the original CI intentionally treats them as non-fatal. If no result files match, the default required: true fails the task with a required-artifact error. Set required: false only when results may legitimately be absent; the run continues and reports that the optional result was not found. Do not declare synthetic or empty JUnit results when tests did not run. For containerized tests, write the XML into a mounted workspace path so Shunter can collect it after the container exits.

For an npm test script that ends in the test runner, append its JUnit flags after npm test --, as in the Node gallery example. When a script chains commands (for example tsc && xo && node --test), npm appends those flags only to the final command. Prefer splitting such a chain into separate lint, typecheck, and test tasks, with the JUnit declaration only on the test task: this shows which step failed and avoids a missing required JUnit file being reported for an earlier failure. Appending flags to the chained command is acceptable when that behavior is intentional and the test runner remains last. If a task command has already failed, Shunter does not add a second required-artifact error just because the JUnit file is missing.

GitHub Actions example with TinyXML2

Section titled “GitHub Actions example with TinyXML2”

Use TinyXML2 at commit 8224e427b655b83dae5e2298f1e6919523a78737. The upstream workflow runs a matrix across three operating systems and two CMake versions. Each job builds and tests four library variants, installs them into a shared prefix, and runs consumer tests against that installation. Pinned upstream workflow.

Original behavior Where it goes
Push, pull request, and manual triggers. Separate jobs per OS and CMake version. The new GitHub workflow keeps those triggers and the Windows and Linux matrix entries. Keep the original macOS entries running in GitHub Actions.
Checkout, MSVC environment on Windows, Ninja and the selected CMake version. The wrapper sets up the same tools before invoking Shunter.
Static and shared libraries in Debug and Release, with a static library suffix on Windows. Four groups in the Flowbook configure, build, and test separate build directories. The wrapper passes the Windows suffix as a variable.
Install all four variants into one prefix and test that consumers can find them. The Flowbook preserves install order and runs all four consumer checks against the same prefix.

  1. Check out the pinned commit in a fresh clone. Copy the TinyXML2 Flowbook to the root as tinyxml2.flowbook. Use Ninja and the CMake version from the matrix entry you want to reproduce.

  2. On Linux, with tree available, run the commands below. On Windows, use a shell with the MSVC build environment and run the Windows variant. The Flowbook runs CTest from each build directory, which works with the older CMake version in the matrix.

  3. Copy the GitHub Actions wrapper to .github/workflows/test-shunter.yml. In your fork with Actions enabled, set the repository variable SHUNT_RUNNER_VERSION to an exact published Shunter runner version and push the two new files. Leave the original workflow in place for the first comparison. The wrapper passes values from its matrix, including the platform-specific install listing command.

  4. Compare each Windows and Linux job with its original counterpart. Check all four library test runs, all four consumer test runs, and the contents of install/, including the Windows library names. Check that the Shunter report opens from the job summary. After the comparison, you can restrict the original workflow to macOS and switch any required Windows and Linux checks to the new job names.

Run each local comparison in a fresh checkout or workspace so cached CMake settings and old install outputs cannot influence the result. Compare 3.15 and 3.x separately and record the resolved tool versions.

In local comparisons on Linux with CMake 3.31.6 and on Windows with CMake 4.1.2, both the baseline and Flowbook passed all eight test runs and installed the same file paths. The Windows check used the CMake bundled with Visual Studio. The CMake 3.15 jobs and hosted matrix still need CI runs before cutover.

Jenkins example with Casino Number Guessing Game

Section titled “Jenkins example with Casino Number Guessing Game”

Use the tutorial project at commit c5fab1400dd515c87c875c3e0f44f4d70af0be0a and take the completed pipeline from the tutorial’s Add a final delivery stage section as the baseline. The tutorial’s Test stage runs the game and its test executable directly. The Deliver stage creates a tarball and asks Jenkins to archive and fingerprint it. Pinned project · Completed Jenkins pipeline.

Original behavior Where it goes
Start with a clean build directory, configure with CMake, and compile. The Flowbook creates a fresh temporary directory for each run and configures the source checkout from there.
Run the game as a smoke test and run the separate unit test executable. Two named Flowbook tasks run the same executables and propagate their exit codes.
Package the game as casino_game.tar.gz with the member build/casino_game. A Flowbook task creates the same package at the root of the checkout.
Archive and fingerprint the package after successful delivery. A Jenkins stage archives the package after Shunter succeeds. An always block separately archives the Shunter report when it exists, including after a failed task.

  1. Copy the casino Flowbook to the root of the pinned checkout as casino.flowbook. Use Linux x64 with CMake, Make, a C++ compiler, tar, and a pinned Shunter runner on PATH. Run the Flowbook from a terminal, then inspect the package and the HTML report.

  2. Copy the Jenkins wrapper to the root as Jenkinsfile.shunter. Create a second Pipeline job that uses the same source and Linux build environment and set its Script Path to Jenkinsfile.shunter. Install the same Shunter runner version on the agent and make sure the Jenkins job can find shunt on its PATH. If your Jenkins controller has mixed agent types, set the wrapper’s agent to your Linux build label.

  3. Run the original and migrated jobs on the same commit. Check that both run the smoke test and the unit tests and that Jenkins archives the package under the same name with a fingerprint. The game uses random values, so compare test outcomes and the archive member list. Check that a failed test skips package archiving and that Jenkins still retains the Shunter report for that run.

In a local Linux comparison, both builds passed and produced a tarball containing build/casino_game. Forcing the Flowbook’s unit test step to fail returned exit code 1, skipped packaging, and produced an HTML report. Verify Jenkins’s archive and fingerprint in your Pipeline job.
