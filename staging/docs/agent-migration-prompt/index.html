Shunter CI migration prompt

Use this prompt with any coding agent: Codex, Claude Code, Cursor, Copilot, Grok, or another tool.

Full prompt

Section titled “Full prompt”

Migrate this repository’s existing CI build and test behavior into Shunter Flowbooks. Do not assume any prior context.

  1. Pick the closest migration gallery example and copy its structure and style. Follow the first CI report walkthrough; leave the original CI in place.
  2. Read the agent guide at https://github.com/getshunter/shunter/blob/main/docs/for-agents.md (or the checked-out docs/for-agents.md) and read the schema with shunt schema or from the published Flowbook schema linked by the guide. Treat the schema as authoritative; do not invent fields or task types. Use shunt validate <flowbook> --format json when structured diagnostics help; otherwise read the human fix hints.
  3. Inventory the CI configuration (GitHub Actions, GitLab CI, Jenkins, Azure Pipelines, and any other CI files present), plus every build/test script those files call. Follow reusable workflows, shared libraries, composite actions, and scripts sufficiently to understand actual behavior. Record triggers, jobs, matrix entries, environments, conditions, tests, artifacts, and failure behavior. Record secret names only, never values.
  4. Create Flowbooks that preserve the original portable build, test, and packaging behavior. When a command depends on a machine-specific tool name or path (for example python3 versus python, or a compiler path), define a Flow variable such as Python: $settings{tools.python3:-python3} with the upstream name as the default, then use ${Python} in commands. Use tools.<name> keys for tool names or paths, keep the upstream default, and add one sentence to the report explaining any local override. On Windows, python3 may be the Microsoft Store alias and exit 9009; keep the default and report this as a platform gap. Read machine settings. Set flow-level working-directory: ${FlowbookDir} on every Flow; keep task-level directories only when a step really runs elsewhere, and relative task-level directories resolve under the Flow default. Prefer one Flow for each build variant or CI job kind (for example windows-build, ubuntu-build, sanitize, or analyze) and each standalone stage (such as install-dev, tests, lint, docs, or coverage). Put shared setup in a Flow called by the others. Keep a short main Flow that calls its stages in order with run-flow; one wrapper remains the default. For matrix jobs, cells can call a variant Flow directly with --flow, or pass Job/Os to the main Flow, which dispatches through one if/else-if chain whose branches contain only run-flow tasks. Do not put inline task bodies under dispatch branches. Small option differences stay as variables or short conditions inside the variant Flow. Do not duplicate tasks per matrix cell; matrix values used only to select a Flow are not Flow variables. Keep OS-only setup and services in the wrapper and list them as gaps. Give each additional Flow or wrapper a one-line justification in the report, such as a different trigger or publish/deploy side effect. Keep each Flow below about 150 lines and at no more than two top-level if blocks; split longer Flows by variant or stage. When one CI step or package script chains independent checks with tests, split lint, format and typecheck into separate tasks that call the underlying tools directly. Give each check stop-on-failure: false and fail-run-on-failure: true; keep install, build and prerequisite tasks at the default. Shunter reports every failure in one run, while a chained script stops at the first; the split is allowed and does not change upstream command semantics. If tox or nox runs several environments, use one task per environment (for example tox -e lint and tox -e tests) and flag check environments; call underlying tools directly only when the CI itself does. A wrapper job can run the whole Flow or select tasks. Preserve generated task names; use exactly one nonblank comment task immediately above the task it labels, with name matching properties.comment. The comment says what the step does and does not repeat its command or migration provenance. Put extra context, including why checks were split, in the comment task’s task-level description and a Flow overview in the Flow’s description; a blank comment task used as a visual spacer omits name and has properties.comment: ''. In each task list, put a spacer immediately before every label comment after the first; never lead or end a list with one, double them, or give a spacer a name. Keep comments presentational. Otherwise preserve upstream command semantics. Keep provider scheduling, runner setup, credentials, caches, services and publishing in wrappers where Shunter has no equivalent. Store direct test-runner JUnit output under .shunter/ (for example .shunter/junit/tests.xml) and use --html-log .shunter/report.html locally; make sure the output directory exists or is created by the tool. When the test runner can emit JUnit, add its output flag to the test task only, attach the produced file, and note the allowed command change in the labeling comment task’s task-level description; never attach a file the command does not produce. If installation itself builds (for example through npm’s prepare lifecycle), keep it as one install task at the default; do not add a separate build task or use --ignore-scripts, and note the nested build in the labeling comment task’s task-level description. By default, keep one <project>.flowbook at the repository root unless the project already has a CI folder convention, and ensure the wrapper’s file: path matches. Do not alter existing CI files unless explicitly asked.
  5. Follow the guide’s mandatory loop until green: run shunt validate, run the Flowbook locally with equivalent tools and inputs, read the HTML and JSON report, fix issues, and repeat. Compare JSON testResults with the number of <testcase> elements in the JUnit file written by the command; they must match, and zero is a defect. Then compare with the runner’s own total. A difference is acceptable only when the runner’s reporting shape explains it (for example, Node writes parent tests with subtests as <testsuite> elements); record that explanation in the report. When a task fails for a reason outside the Flowbook, run the project’s own CI command (for example npm test) on the same machine. If it fails the same way, report an upstream or platform failure with quoted output, keep the Flowbook unchanged, do not edit project files or skip the task, and confirm every other task still ran; otherwise fix the Flowbook defect. Continue until green, or until the only failures are documented upstream failures. Before finishing, remove run outputs created during validation or list any retained in the report. Never commit .shunter/ or test-runner JUnit output, and do not add project .gitignore entries unless asked. Do not claim an unrun test passed.
  6. Report a mapping table from every original job/step to a Flowbook task or wrapper location. Include evidence, gaps, assumptions, and behavior you could not verify. State whether the first run passed and how many validate/run fix-up cycles were needed.
  7. Never read, copy, print, or commit secret values. Never push changes. Commit with the repository’s configured git identity; do not change git config. Do not change original CI files unless the user asks.

Small-context variant

Section titled “Small-context variant”

Read only the authoring checklist, CI concept mapping, mandatory validation loop, and common mistakes in for-agents.md; consult the task reference/schema for each task you use. Then follow steps 2–6 above. If you cannot read the guide URL, use the checked-out docs/for-agents.md; if neither is available, stop and report that the required format contract could not be read. Do not guess schema keys.
